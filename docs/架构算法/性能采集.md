# 性能采集

> 基准： 0.6.0 / 2026-10-14

`@nexus-kit/runtime/perf` 回答三类问题：**这一局越跑越卡、越跑越占内存，是从哪一刻开始的**（水位长线）、
**点开图标后白屏那几秒花在哪**（启动画像）、**上一局闪退前最后几分钟是什么状态**（跨会话保留的水位）。
数据全部进诊断文件，kit 不画界面。需求证据与分期见设计稿存档[运行时基础设施](../存档/运行时基础设施_2026-10-14.md) §3，
诊断文件的合成与交付见[日志与诊断](日志与诊断.md)。

## 1. 一局里的采样

拿模板走一遍。`src/observe.ts` 在渲染前执行 `createPerf({ prefix, store: logs, version, build })` 和 `start()`：

1. `start()` 立刻采一个基线点，之后每 5 秒（`sampleMs`）采一个点；页面转入后台时补采一个，切走之前的状态
   不会丢在两次定时之间。
2. 一个采样点是 `{ t: 墙钟毫秒, v: { 指标名: 数值或 null } }`。内置指标是本区间的帧统计（`fps`、`hitches`、
   `worstMs`、`workMs`）、`heapMB`（JS 堆，只有 Chromium 给）、`dom`（DOM 节点数）、`storageMB`（站点存储用量）、`longTasks` / `longTaskMs`（本区间长任务，只有 Chromium 给）。宿主经
   `registerGauge(名字, 读数函数)` 登记的指标同一时刻各读一次；kit 的图像缓存和音频播放器传了 perf 时也经它登记
   （`assets.*`、`audio.decodedMB`，见[图像资源](图像资源.md) §4、[音频](音频.md) §3）。读不到、读数抛错或不是有限数一律记 null，
   不记 0、不中断采样——Safari 没有 JS 堆，记 0 会让人误以为堆是空的。读数抛错时日志里按「哪个指标、什么原因」
   只记一条 warn，免得一个坏指标每 5 秒刷一条，也免得它一直是 null 却没人知道。宿主指标不能用内置指标名和
   `t`、`kind`、`session`（JSONL 行字段），`registerGauge` 遇到这些名字直接抛错。
   `storageMB` 来自 `navigator.storage.estimate()`，这是跨进程的配额查询，不便宜，所以最多 60 秒读一次、页面隐藏
   时不读；读数是异步回来的，采样点取最近一次读到的值，因此基线点的 `storageMB` 总是 null。
3. 采样点推进内存里的环形长线（默认 2048 点，5 秒一点约 2.8 小时），然后把本局长线写盘（见 §3）。
4. 导出时 `trend()` 对每个指标给出首值、末值、净增、峰值和峰值出现在第几秒。判泄漏只看长线的走势：
   截面数字高不说明问题，从第 10 分钟起一路涨不回落才是。

帧统计有两种来源。普通应用由 `requestAnimationFrame` 自测相邻两帧的间隔，得到帧率与卡顿：间隔超过 50ms
记一次卡顿，卡顿明细（时刻与时长）留最近 200 条。自己有渲染循环的宿主（游戏）在每帧首尾调
`frameStart()` / `frameEnd()`，额外得到每帧的工作耗时 `workMs`；第一次调 `frameStart` 时 rAF 自测自动停掉，
两边不重复计数。间隔超过 1 秒算暂停（切后台时 rAF 停摆、宿主循环被冻结），既不算卡顿也不进帧率，否则切一次
后台就会多出一个「卡了 30 秒」的假卡顿。

## 2. 启动画像

一条启动画像是一次启动的低频摘要：导航分段耗时（重定向、SW 唤醒、首字节、响应、解析、DCL、load）、宿主经
`span` / `spanAsync` 记的阶段耗时、经 `milestone` 记的时间点（距导航开始的毫秒数）、按类型（js、css、img、
font、media、data、other）汇总的资源、最慢的几个资源（地址去查询串）、本次是否由 SW 接管。

资源汇总把「走网络的字节」和「缓存命中数」分开记：`transferSize` 为 0 且响应体不为空算缓存命中，不计字节。
首次真下载慢和二次读缓存慢的治法完全不同——前者要减体积，后者要查 SW 唤醒和磁盘。

模板采两次：根组件挂载时（`onAppMounted`）采一次兜底，`load` 事件之后再采一次完整的。两次的会话号相同，
后一次覆盖前一次，不占两个名额。画像存在 localStorage `<prefix>.boot`，留最近 5 次（`bootKeep`）；写不下时
退到只存这一条，再不行就放弃，不抛错。导出时「启动画像」一节列最近 3 次。浏览器的 Resource Timing 缓冲默认只存 250 条，资源超过 250 个的应用，
画像里的资源汇总只覆盖前 250 个；kit 不改这个全局缓冲的大小，宿主需要时自己调 `performance.setResourceTimingBufferSize`。

## 3. 跨会话保留

内存里的长线刷新即失，而排查闪退最需要的正是上一局最后几分钟。每次采样后，`persist.save` 把本局长线的最后
120 个点（`keepSamples`）写进 localStorage `<prefix>.vitals`。这个键存一张会话表，每个会话一行
`{ updatedAt, samples }`。每次写都是「读整表 → 只改本行 → 写回」：同一应用开在两个窗口时各写各的行，互不覆盖。
表里只留本局加最近 2 个其他会话（`sessionsKept` 默认 3）。

举例：会话二运行中被系统杀掉。它最后一次采样在死前 0~5 秒内，那一行停在那里。用户重新打开（会话三）、
连点版本号导出，诊断文件里「其他会话最后的水位」一节和附录的 `savedVital` 行都带着会话二的会话号，可以和
日志里会话二那一段对上。

这个设计有两条边界。第一，死前最后 0~5 秒的变化没有记下来，采样间隔就是精度。第二，会话二被挤出会话表
之后就读不回来：用户在出事后又打开了两次以上才导出，现场就没了；同时开着三个以上窗口时，活着的窗口会立刻把
它挤掉。多个窗口的「读整表 → 写回」不是原子操作，两个窗口恰好同时写时，后写的会盖掉对方刚写的那一行，
对方下一次采样（5 秒内）重新写回。kit 不另设「出事时冻结」的保护槽，
因为疑似异常的判词本身也只是「缺少正常告别」，冻结会把正常的被系统回收也当成现场长期占位。坏行只丢该行，整表不是合法 JSON 时记一条 warn、按空表处理，下次写盘覆盖掉；读写失败不抛错，同一原因只记一条 warn。
启动画像的读写失败同样处理。

## 4. 进诊断文件

`createPerf` 往日志 store 登记三节摘要和一个附录：

- 「启动画像」：最近 3 次画像，每次一行概要加分段明细；
- 「性能走势」：本局点数、跨度，每个指标「首值 → 末值（净增，峰值 @ 第几秒）」；
- 「其他会话最后的水位」：每个其他会话的点数、最后更新时间和最后一个点；
- 附录「性能数据（JSONL）」：一行一个 JSON，首键 `kind`，取值 `meta`（会话、版本、采样间隔）、`trend`、
  `vital`（本局每个点）、`savedVital`（其他会话的点，带 `session`）、`boot`、`milestone`、`span`、`hitch`。

摘要节进日志头部，人打开文件先看到结论。附录排在日志之后（`registerAppendix`），可以按 `kind` 逐行过滤，
例如 `grep '"kind":"vital"'` 后画图。复制到聊天时模板调 `exportText({ appendix: false })` 去掉附录：附录体积大，
复制的截短逻辑只针对日志行。

## 5. WebGL 记账（可选）

自己用 WebGL 的宿主可以调 `installGlCounter(gl)`，再把 `counts()` 的几个数登记成 gauge。它包住上下文的创建、
删除和上传方法：按创建减删除记纹理、缓冲、帧缓冲的净存活数，按第 0 级上传的宽 × 高 × 4 估算纹理字节，
另记峰值。绑定按「纹理单元 × 目标」记（包住 `activeTexture`），上传记到当前单元绑定的纹理上。图像源的尺寸取
真实像素：`<img>` 用 `naturalWidth`（`width` 可能是 CSS 缩放后的），视频用 `videoWidth`，`VideoFrame` 用 `displayWidth`。
安装前已存在的对象用 WeakSet 区分，删除它们不会把计数减成负数。估算把压缩纹理、非 RGBA8 格式、
mip 链都按 RGBA8 第 0 级算，只是量级参考。kit 不读 Pixi 等渲染库的内部账本：渲染库以为释放了、GL 层没释放，
两本账背离本身就是泄漏线索。`uninstall()` 还原被包住的方法。上下文丢失（`webglcontextlost`）后 GL 对象全部失效，计数器不会自动清零，宿主
在恢复时重新装一个计数器。

`dispose()` 停定时器、停帧测、断开长任务观察并注销导出摘要。之后再调 `start()` 抛错：摘要已经注销，静默再跑
只会采到不进诊断文件的数据。

## 6. 验证

单测注入时钟、rAF、存储和 performance 接口，覆盖帧统计与暂停判定、环形与走势、会话表的多窗口与淘汰、
画像的分段与缓存口径、GL 计数（`packages/runtime/src/perf/*.test.ts`）。真浏览器 e2e（`scripts/e2e-diagnostics.ts`）
在「刷新 → CDP 杀进程 → 重开导出」这条链上断言：诊断文件有启动画像与性能走势两节，附录有各类行，被杀掉那一局的
`savedVital` 读得回来，复制内容不带附录。iOS 上被系统杀掉前最后一次采样能否写盘，只能真机验证。
