# 文档写法规范

> 基准： 0.1.0 / 2026-10-13

本篇规定文档放哪、怎么写、怎么和代码保持同步。`pnpm docs:check` 是它的机器门禁。

## 1. 分层：每层只回答一类问题

| 目录 | 回答 | 性质 |
|---|---|---|
| `docs/需求/` | 做什么：范围、裁决、验收口径 | 活文档 |
| `docs/架构算法/` | 怎么运作：机制、原理、数据流、算法口径 | 活文档 |
| `docs/规范/` | 必须遵守什么：可执行、可检查的规则 | 活文档 |
| `docs/设计/` | 打算做什么：实施方案与进度 | 活文档（完结即存档） |
| `docs/存档/` | 当时是什么：历史快照 | 冻结，永不更新 |

1. 需求域收在 `docs/需求/`：`需求.md` 总文档统一记需求、裁决与实施状态；口径登记类文档同目录维护；
   不为需求派生子任务详设，历史子稿进存档，仍有效的口径先并入总文档再归档。
2. 架构文档只写机制和原理；源码行号、实测数据、格式证据这类证据性内容不进架构正文。例外是被规范
   点名的**登记册**（口径唯一真源，如坑账、真值表），随架构目录维护。
3. 设计稿完结后整体移入存档，机制部分先并入对应架构文档。

## 2. 三条写法铁律

4. **只写定稿，不打补丁**：正文只写现行事实（「X 是 Y」），禁止「从 A 改为 B」「某日修订」「已废弃」
   「不再……」等过程叙述；改口径时直接把旧写法改写成新写法。过程摘要一行一条记进该文档末尾的
   「变更记录」节（`- YYYY-MM-DD 摘要`，最新在上），详细过程归 git log 与存档。例外：仍影响运行时行为
   的存量规则（如「旧 key 不读不迁」）按现状事实写进正文。
5. **不写死可再生的数字**：条数、体积、分布等脚本能算出来的数据，一律指向审计/统计命令输出。
6. **原理写透，细节不复读**：核心算法与机制用通俗文字 + Mermaid 图讲清；类型逐字段表、函数签名、
   常量清单以代码为准，不抄进文档——两处各维护一份必然漂移。

## 3. 元数据

7. 每篇活文档头部前 20 行有「基准： 版本/日期」= 最后一次与代码核对过的时间点。触及哪篇，先补同步
   再 bump 基准；发版时过一遍。
8. 设计稿头部前 20 行有「状态：」行，它是进度的**唯一**记录处；索引、架构文档、验收报告都不维护进度表。
9. 每篇活文档必须登记到 CLAUDE.md 的文档索引，新文档同提交登记。
10. 命名「主题.md」，不带编号、日期、版本号、过程后缀（方案/定稿/v2）；存档统一「主题_YYYY-MM-DD.md」。

## 4. 同提交同步

11. 文档更新与对应代码同一提交，不允许「代码先行文档后补」：改功能 → 需求文档；改机制/算法 → 架构文档；
    改必须遵守的规则 → 规范；改用户可见文案 → 文案规范（如有）。
12. 横切面自查：新增用户可见文案、颜色、日志标签时，回对应规范的词典登记（项目有这类规范时）。
13. 文档移动或改名时，同提交更新全部互引与 CLAUDE.md 索引。

## 5. 产物归位

14. 临时验证产物放 `temp/`（不入库）；验收/审计报告放 `reports/`（入库，按「主题 + 日期」归档，只增不改）。
