# 工程质量与交付规范

> 基准： 0.7.0 / 2026-10-15

本篇规定代码如何通过质量门禁、测试、构建、评审和发布。运行时合同见
[Web 运行时开发规范](Web运行时开发规范.md)，文档纪律见[文档写法规范](文档写法规范.md)。违反任何一条即返工。

## 1. 唯一完成标准

1. 普通改动以 `pnpm check` 全绿为完成标准（文档审计、lint、类型、单测、构建含 verify-build），任何一步
   失败都算未完成；失败必须贴原始输出如实报告。
2. 发布候选还必须通过需求文档规定的真机验收（安装、断网打开、升级、安全区）。
3. 验证命令不得修改已跟踪文件。跑完出现的新差异必须查明来源，不得当噪声直接提交。

## 2. 代码边界

4. 外部数据（网络 JSON、存储、URL 参数、文件、浏览器 API 返回值）先作 `unknown`，在边界校验后才进业务对象；
   禁止把 `response.json()` 直接强转为业务接口。
5. 错误不许静默吞掉：要么向上抛、要么进结构化日志并给出明确结果（阻断、可见重试、登记过的降级）。
6. 密钥一律走环境变量，绝不进源码与配置文件。
7. 出现重复的加载、校验、清理或配置逻辑时，先收敛公共入口，再增加新调用点。
8. 纯逻辑与副作用分离：时间、随机、网络、存储经依赖注入，规则代码可在 Node 里单测。

## 3. 测试分层

9. 有明确输入输出的逻辑（算法、数据转换、状态机、业务规则）先写测试再写实现；bug 修复先用能复现的
   失败测试钉住。
10. 产品源码覆盖率四项守 80%；降阈值、按「是否被测试导入」筛源码、写只为做绿的假测试都是造假。
11. 三类例外不写单测，但必须换一种方式验证并在交付时说明：一次性脚本与调试探针；随时会推翻的原型；
    纯视觉/表现层（用视觉回归或人眼验收）。
12. 单测不得依赖个人绝对路径、真实网络或机器上已有的数据；固定输入必须得到稳定结果。
13. 行为金样变化必须说明来源，禁止只为做绿覆盖期望文件。

## 4. 构建与版本

14. `pnpm build` 是唯一构建命令（`vite build` + 构建后门禁），日常验证与发布同一条路；构建不得修改源码。
15. 产品版本由 package.json 人工维护，纯 `X.Y.Z`；构建号 `.build-number` 每次构建自动 +1、不入 git，
    主仓真身、工作树软链共享。计数器丢失后发版前必须核对线上 version.json 的 build 再写回。
16. 版本进位的判据是用户能不能感知到变化：新增或改动用户可见的功能、界面、文案，修掉用户能察觉的问题，
    都要在提交前提醒负责人进位；门禁、文档、构建脚本、内部重构不进位。版本号由负责人拍板，任何人不得代改。
17. CHANGELOG 是发版变更的唯一台账：源码提交必须附条目（precommit 门禁，`pnpm hooks` 启用）；用户无感的记
    「内部：」，主干上未开放的功能记「WIP：」，纯重构/文档/测试可 `--no-verify` 跳过。
18. 依赖安装使用锁文件和固定 pnpm 版本；依赖变更同时提交锁文件，主要框架升级必须跑发布级回归。

## 5. 发布

19. 发布链：整合 CHANGELOG 的 Unreleased（合并同类项、只留用户可感知要点、5 条以内、大白话）并落款
    `## [版本号] - 日期` → 对上个 tag 到 HEAD 的全量变更跑一次独立代码评审 → 真机走查本版对外条目 →
    `pnpm release --ack`。`pnpm release` 是唯一发版入口：校验主仓库、主干、干净、落款小节（日期是今天、有对外
    条目、无「WIP：」条目）、tag 未占用，然后放发版锁，依次跑 `nexus.config.json` 的 `release.steps`（默认
    `pnpm check` → `pnpm build` → `pnpm run deploy`），每步后核对 HEAD 未变，打 tag `v<版本>` 并推送，最后收锁。
    不带 `--ack` 只报发版范围与两道门禁，不碰线上。不得手工打 tag 或手工部署代替发版链。
20. 有其他改动线在并行时，落款前先 `pnpm release:lock` 冻结主干：命令打印一个令牌，发版执行人在自己的会话
    `export NEXUS_RELEASE_TOKEN=<令牌>`，落款与评审修复的合入凭令通过；其余会话对主干的一切更新被
    reference-transaction 钩子拒绝，等发版完成再合。`pnpm release --ack` 认领这把锁续跑，链末自动收锁。
21. 发版链中断或进程被杀会留下残锁，残锁到期自动失效；确认没有发版在跑时可 `pnpm release:unlock` 清除。

## 6. 并行开发

22. 同时推进多条改动线时用 git 工作树隔离，不在一个工作目录里来回切分支；不用 `git stash`（全仓共用，
    会在别的工作树弹出），中断改用 WIP 提交。
23. 建工作树只走 `pnpm worktree:new <分支名>`；`claude --worktree` 与子 Agent 的 `isolation: "worktree"` 经
    `.claude/settings.json` 的钩子走同一入口。不得手工 `git worktree add`：手工建的树不挂共享软链（构建计数器
    会各算各的），也不登记端口。
24. 工作树里的预览服务用建树时登记的端口（`pnpm worktree:ls` 查），起服务加 `--port <端口> --strictPort`；
    端口撞了会静默连到别的检出，看到的不是自己的代码。
25. 合入前置：任务做完、`pnpm check` 全绿、独立评审过；在工作树 `git rebase main`，并在变基后的代码上重新验证（变基带进了别人新加的依赖、锁文件变了的话，先 `pnpm install`）。
    合入时主干又前进了，重新变基、重新验证。
26. 合入只走 `pnpm worktree:merge <分支名>`，单独执行，不与检查、回收用 `;`、`&&` 串成一条，看清退出码再走下一步。
    脚本只做快进：分叉即拒绝，回工作树变基；另一个合入正在进行时立即拒绝，等它完成后变基、重新验证再合；
    被发版锁拦下时脚本自动把主仓库的合入残留还原。合入后脚本在主仓库先按锁文件装依赖、再跑 `pnpm build`，失败表示主干当前构建
    不过，必须继续修（修复同样走工作树合回），不得当成功收工。不得在主仓库手工 `git merge`、解冲突或提交。
27. 确认合入成功后才回收，回收只走 `pnpm worktree:rm <名称>`：它先停掉该树起的服务与 pm2 应用再删目录，
    遇到未提交改动或不可再生的被忽略文件拒绝执行。不得直接 `git worktree remove` 或 `rm -rf` 工作树目录。
28. `nexus.config.json` 的 `worktree.share` 列出的路径在工作树里是指向主仓库的软链，在工作树里重新生成它会
    写回主仓库；需要本树独立的一份时先 `pnpm worktree:isolate <共享项>`。
29. 关键命令（build/test/check/deploy/worktree:merge/release）后不得接裸 `| tail`、`| head`——管道吞掉退出码
    会伪造成功。

## 7. 提交与评审

30. 每个提交只包含一个可验证切片，使用 conventional commits，代码与对应活文档同提交。
31. 代码写完提交前跑独立视角的代码评审；改了产品行为（玩法、交互、用户可见文案、默认值）再加一道产品评审。
32. 阻断问题修复后必须复审；评审结论记录实际运行的命令、未覆盖范围和剩余风险。

## 8. 部署

33. 生产部署只走 `pnpm run deploy`（不能写 `pnpm deploy`，会被 pnpm 内置命令遮蔽）：发版时由 `pnpm release`
    链调用，单独执行只用于把已发布的版本重新部署；只在主仓、发布分支、工作树干净、刚构建完时执行；流程含缓存头预检、原子切换、回环冒烟与失败自动回滚，不得手工跳过冒烟。
34. 回滚 = 服务器把 current 软链切回旧版本目录，秒级、无需重新部署；回滚后必须冒烟确认 version.json 指纹。
35. 缓存头红线：`index.html`、`sw.js`、`version.json`、`manifest.webmanifest` 必须带 `private, no-cache`；带哈希
    的 `assets/` 走 `public, immutable`。改 nginx 或 CDN 规则视同改门禁，必须线上验证。
